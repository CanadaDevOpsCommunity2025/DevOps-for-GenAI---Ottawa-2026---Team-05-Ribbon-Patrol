# 1.2 AI route aliases and asset approval

## Objective

Expose the specification-compliant AI routes without breaking current clients.

### Scope

Update `server.ts`. Keep existing `/api/chat` and `/api/images/*` routes available.

### Required routes

* `POST /api/ai/chat`
* `POST /api/ai/images/generate`
* `POST /api/ai/images/edit`
* `POST /api/ai/images/:id/approve`

Aliases must use the existing handlers or shared service functions. Do not duplicate model logic.

### Asset approval requirements

The approval endpoint accepts an existing preview ID. It validates the ID and promotes only that generated asset to the pet asset set.

Return a stable response containing the approved asset ID and asset metadata. Reject unknown, expired, or malformed IDs with a safe client error.

### Request and response requirements

Chat requests accept a user message and the sanitized repository snapshot. Image creation accepts the selected style, target health state, ratio, and visual request. Image editing also identifies the approved source asset.

All success responses return a request ID. Chat responses retain the validated action fields: summary, evidence, recommendation, confidence, expected impact, and reversal. Image responses distinguish temporary previews from approved assets.

Use consistent client-safe failures. Validation failures identify the invalid field. Rate limits and service failures offer a retry path. Internal provider details never reach the client.

### Approval lifecycle

1. Generate or edit a temporary preview.
2. Validate ownership, expiry, and supported health-state mapping.
3. Promote the selected preview only after an explicit approval request.
4. Return the approved mapping and retain prior assets for rollback.

Approval must be idempotent. Repeating a successful approval returns the same approved asset state. A failed approval must not alter the current mascot asset.

### Compatibility and observability

The specification route and its existing route must share one validation and service path. Both must produce equivalent successful and failure responses.

Record request IDs, endpoint name, status, and latency. Redact tokens, audio, repository paths, prompts where required, and image data.

### Safety requirements

* Preserve request validation, payload limits, and request IDs.
* Never log tokens, image payloads, or repository paths.
* Approval must not access repository content or execute Git commands.
* Return explanation-only errors for unsupported model output.

### Acceptance criteria

1. Each `/api/ai/*` route returns the same validated behavior as its current counterpart.
2. Existing non-aliased routes continue working.
3. A valid preview can be approved once and becomes the selected asset.
4. Invalid preview IDs return a client-safe error.
5. The route contract stays aligned with the functional specification.
6. Repeated approval requests do not create duplicate asset mappings.
7. Failed generation, edit, or approval leaves the current approved asset unchanged.

### Verification

Use `curl` for every alias and approval path. Run `npm run lint` and `npm run build`.
