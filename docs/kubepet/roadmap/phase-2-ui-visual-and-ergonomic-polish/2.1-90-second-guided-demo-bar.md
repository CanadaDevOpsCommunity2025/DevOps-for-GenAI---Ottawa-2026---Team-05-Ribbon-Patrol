# 2.1 90-second guided demo bar

## Objective

Make the Notice → Understand → Resolve story accessible in one click.

### Scope

Update `src/App.tsx` and the relevant demo-state components. Keep `PitchDeckModal` available as supporting content.

### Required experience

Render a prominent **🚀 90-Second Guided Demo** bar on the main canvas. It controls four deterministic steps:

1. **Clean state** — show a healthy, synchronized repository.
2. **Anomaly injected** — load the behind-remote and local-work scenario.
3. **Status report** — open or populate the evidence-backed guidance.
4. **Safe action approved** — show preview, confirmation, and verified recovery.

Each step clearly indicates current progress. The developer can start, advance, pause, restart, or exit the flow.

### Behavior requirements

* Use existing mock scenario data. Do not create live repository changes.
* Auto-advance only after the step is visibly complete.
* Preserve manual control when users interact with chat or previews.
* Reset transient demo state when restarted.
* Keep the flow usable with keyboard navigation.

### Step definitions

**Clean state** initializes the healthy scenario, closed drawer, and empty guidance state.\
**Anomaly injected** loads the canonical remote-divergence fixture and its pet transition.\
**Status report** displays the required evidence and one safe action card.\
**Safe action approved** opens the preview, requires explicit confirmation, then displays the verified result.

Each step has an expected visible result and a bounded duration. The bar exposes the current step, total steps, and elapsed time.

### Control behavior

Start is available from the initial state. Next becomes available only after the current visual update completes. Pause stops auto-advance without clearing state. Restart restores the initial fixture. Exit retains the current app state but removes demo-only prompts.

If a modal is required for the next step, the bar directs focus there. If the developer closes it, the bar shows the next required action rather than silently advancing.

### Failure handling

Mock data or UI failures must show a retry action. The demo cannot depend on a live model, microphone, local repository, or image provider. Use deterministic local responses where a remote dependency is unavailable.

### Acceptance criteria

1. Starting the demo reaches all four steps in under 90 seconds.
2. Every step produces the expected pet, evidence, and action UI.
3. Approval still requires an explicit confirmation interaction.
4. Restart returns the app to a clean initial state.
5. The demo remains deterministic across repeated runs.
6. Pause, restart, and exit preserve their documented behavior.
7. The bar reports an actionable retry state when a step cannot complete.

### Verification

Run the full sequence twice. Check visual transitions, citations, diff preview, confirmation, celebration, and streak update.
