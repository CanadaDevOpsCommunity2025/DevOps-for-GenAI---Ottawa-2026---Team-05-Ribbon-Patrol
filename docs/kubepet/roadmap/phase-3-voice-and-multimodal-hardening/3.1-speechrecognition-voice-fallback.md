# 3.1 SpeechRecognition voice fallback

## Objective

Provide a browser speech-to-text fallback for voice guidance.

### Scope

Update `src/components/LiveVoiceModal.tsx`. Preserve the Gemini Live WebSocket as the preferred low-latency channel.

### Fallback behavior

Use `SpeechRecognition` or `webkitSpeechRecognition` when Live audio fails, disconnects, or is unavailable. Capture begins only after the developer presses push-to-talk or starts the microphone.

Show interim and final transcripts. Allow the developer to edit the final transcript before sending it through the standard typed-chat path. Keep live-mic mode and push-to-talk controls clearly separate.

### Requirements

* Detect support before presenting the fallback control.
* Request microphone permission only after a direct interaction.
* Expose start, stop, mute, and retry states.
* Stop playback and active capture when the developer interrupts.
* Show a typed-input path when browser recognition is unsupported.
* Do not persist raw audio or transcripts beyond the active session.

### Channel selection

Prefer Gemini Live when a session exists and the connection is healthy. Fall back to browser recognition only after a connection failure, unsupported transport, or explicit fallback selection.

Do not switch channels silently while recording. Explain the active channel and show when the fallback is listening. The developer may return to Live after a successful reconnection.

### Transcript lifecycle

Interim transcript text is visibly provisional. Final text becomes editable before submission. Sending uses the same validated typed-chat request and sanitized snapshot as keyboard input.

Clear unsent interim text when capture stops. Retain final editable text until sent, discarded, or the modal closes. Do not attach audio data to the chat request.

### Browser and permission states

Distinguish unsupported recognition, insecure context, microphone denial, busy microphone, unavailable network recognition, and no-speech timeout. Every state offers a clear recovery action or typed alternative.

Spoken replies remain optional. Stopping capture must also stop any active speech output when the developer requests interruption.

### Acceptance criteria

1. A Live connection failure offers browser recognition when supported.
2. A completed transcript can be edited and sent as chat.
3. Unsupported browsers retain an obvious typed alternative.
4. Capture stops reliably on stop, close, and permission denial.
5. Repository writes still require preview and explicit approval.
6. The active input channel and transcript state remain visible throughout capture.
7. Permission and support failures provide a clear typed recovery path.

### Verification

Test supported, unsupported, denied-permission, and dropped-WebSocket paths. Confirm typed chat receives the same sanitized repository context.
